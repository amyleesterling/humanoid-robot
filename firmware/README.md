# HR-V0 firmware release area

> **PRELIMINARY—NOT APPROVED FOR FABRICATION OR ENERGIZATION**

This directory contains the first controlled implementation candidate for the HR-V0 watchdog and motion-authority supervisor. It is deliberately split into:

- `watchdog/`: portable C logic intended for the proposed RP2040-class watchdog controller;
- `supervisor/`: Python authority/state-machine code intended for the HR-V0 Raspberry Pi; and
- `SOURCE-MANIFEST.csv`: SHA-256 hashes generated by `tools/check_hr_v0_firmware.py --write-manifest`.

The watchdog firmware drives two ordinary relay channels and checks their conditioned NC diagnostic contacts. It receives no functional-safety credit. The hardware SR1 RESET then SRA1 ARM/EDM chain—not this firmware—must prevent heartbeat restoration from restoring K1/K2.

The supervisor has no output capable of closing K1 or K2. It may request actuator torque only after observing the released hardware sequence and accepting a fresh, configuration-matched trajectory. RESET and physical ARM never create a motion command. The current P0.4/P0.3 source binds the 15–115° J2 envelope to the held `HR-V0-ARM-ARCH-P0.8-DWG-INTEGRATED-CANDIDATE`, records `HR-V0-ARM-ARCH-P0.7` only as its inherited kinematic basis, binds the exact custom-part manufacturing identity to `HR-V0-MECH-BOM-BIND-P0.2`, and retains `HR-V0-HS-P0.3`. Its unresolved external-current evidence remains bound to `HR-V0-DXL-CURRENT-ENV-P0.1`. `dynamixel_bus.py` and `sdk_transport.py` retain torque-off-before-discovery, exact bus identity, ordered configuration, trajectory-bound synchronous writes and fault-triggered torque removal. Every motion-sample poll re-reads Current Limit and Goal Current; any drift from the configured candidate forces torque-off. R236 adds the required `HR-V0-EVID-LOG-P0.1` hash-chained evidence sink; an open/write failure prevents start or enters fail-closed runtime cleanup. The committed acceptance, calibration, timing and storage selections remain unresolved, so the serial port cannot open. Raw current values and source log tests are guarded candidates, not released physical evidence or functional-safety controls.

## Current evidence and limits

Run:

```text
python tools/check_hr_v0_firmware.py
```

The checker runs the executable Python unit tests, checks the portable C interface/constants and DYNAMIXEL transport invariants against the controlled configuration, and verifies the source manifest and pinned SDK record. It does not install the SDK, open a serial port, compile a new RP2040 binary, or perform hardware-in-the-loop testing.

Before this area can be released, the project still needs:

1. compiled binding for the frozen GPIO candidate plus exact connectors, default-off drivers, 24 V feedback interfaces, received polarity and debug-interface selections;
2. a reviewed Pico SDK platform binding and pinned toolchain/container;
3. reproducible `.uf2`/`.elf` binaries with hashes and map files;
4. Raspberry Pi deployment packaging and service supervision;
5. the released kinematic model, received calibration/profile/telemetry limits and target-installed DYNAMIXEL SDK/transport image;
6. received actuator identity/firmware records and external branch-current, torque and thermal characterization under `HR-V0-ACT-P0.3`;
7. HIL traces for every startup, timeout, stuck-signal, feedback, reset, ARM, configuration mismatch, stale-target, unexpected-ID, packet/USB, bus-watchdog and partial-write fault; and
8. qualified controls, electrical and functional-safety review.

No file in this directory authorizes connecting outputs to contactors, installing firmware on the robot, or energizing an actuator.
